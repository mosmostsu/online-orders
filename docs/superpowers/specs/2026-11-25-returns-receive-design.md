# หน้ารับของคืน `/returns` — design

วันที่ 2026-11-25 · ผู้ใช้เลือกแบบ A (ยิงรับ + ดึงสถานะจากแพลตฟอร์ม)

## ทำไม

ร้านจะเลิกใช้ BigSeller ตอนนี้ใช้หน้า "การคืนสินค้า Stock-In" ของ BigSeller เช็คว่า
**ของที่ขนส่งเอามาคืนได้ครบหรือเปล่า** (ผู้ใช้พูดเอง 25 พ.ย.) — ใบไหนควรกลับมาแล้วแต่ยังไม่เห็นของ

วิธีที่ร้านทำใน BigSeller ตอนนี้ (ดูจากหน้าจริง 25 พ.ย.):
- BigSeller ดึงจากแพลตฟอร์มเองว่า "ถึงคลัง" แล้ว (ช่องเวลาถึงคลัง)
- ตอนเย็น ~18:30–19:00 พนักงานยิงกล่องทีละใบ แล้วกด "ไม่ Stock-In" (รับแล้วแต่ไม่ให้ BigSeller นับสต็อก — สต็อกจริงอยู่ Seniorsoft)
- แถบ "ยังไม่ Stock-In" = ใบที่ยังไม่มีคนรับ (80 ใบ ณ 25 พ.ย.)
- ปริมาณ 90 วัน: 1,130 ใบ (TikTok 964 · Shopee 158 · Lazada 8 · ThisShop 0)

## เป้าหมาย

1. เห็นทุกกล่องที่กำลังกลับร้าน ทั้ง **ส่งไม่สำเร็จ/ตีกลับ** และ **ลูกค้าขอคืน (คืนเงิน+คืนของ)**
2. พนักงานยิงบาร์โค้ดบนกล่อง → ระบบหาใบเจอ → จดว่ารับแล้ว (ใคร เมื่อไหร่) + โชว์ว่าในกล่องควรมีอะไร
3. เห็นชัดว่าใบไหน **ขนส่งบอกว่าส่งถึงร้านแล้วแต่ยังไม่มีใครยิง** = ของอาจหาย ต้องตาม
4. เห็นใบที่ค้างเดินทางนานผิดปกติ และใบที่แพลตฟอร์มบอกว่าสูญหาย

## ไม่ทำ (non-goals)

- **ไม่กดอะไรบนแพลตฟอร์ม** — ยอมรับ/โต้แย้งคืนเงิน, ยืนยันรับของคืนใน TikTok/Shopee ยังทำในแอปแพลตฟอร์มเหมือนเดิม (ย้อนไม่ได้ + กระทบเงิน)
- ไม่ตัด/เพิ่มสต็อก Seniorsoft (คนยังคีย์รับคืนเองเหมือนเดิม)
- ใบ "คืนเงินเท่านั้น" ที่ไม่มีของกลับมา ไม่ต้องขึ้น
- ThisShop (ยังไม่มีใบคืนเลย)

## Anti-goals (ถ้าเป็นแบบนี้ถือว่าพลาด)

- พนักงานยิงแล้ว "ไม่เจอ" บ่อย → กลับไปใช้ BigSeller
- หน้ามีใบเก่าค้างเต็มไปหมดจนหาใบที่ต้องตามไม่เจอ

## ข้อเท็จจริงจาก API (ทดลองยิงจริง 25 พ.ย. อ่านอย่างเดียว)

| เรื่อง | TikTok | Shopee | Lazada |
|---|---|---|---|
| ตีกลับถึงร้านแล้ว | `GET /fulfillment/202309/orders/{id}/tracking` → event `action_code 80101` "returned to the seller" (เวลาตรงกับ "ถึงคลัง" ของ BigSeller) | `GET /api/v2/logistics/get_tracking_info` → `tracking_info[].logistics_status = RETURNED` ("ผู้ส่งได้รับพัสดุคืนเรียบร้อยแล้ว") | `raw_status` ของออเดอร์ = `shipped_back_success` / `returned` (มีในตารางอยู่แล้ว) |
| ลูกค้าขอคืน | `POST /return_refund/202309/returns/search` → `return_id, return_status, return_tracking_number, return_line_items[].seller_sku, return_type` | `GET /api/v2/returns/get_return_list` → `return_sn, status, tracking_number, item[], update_time` | `/reverse/getreverseordersforseller` — ยังไม่ได้ลอง (โทเคนในเครื่องหมดอายุ) |
| ลูกค้าคืนถึงร้านแล้ว | ไม่มีสัญญาณ (BigSeller ก็ไม่มี) → ใช้การยิงรับเป็นตัวบอก | ลองใช้ get_tracking_info ด้วยเลขขากลับ/สถานะคืน — ถ้าไม่ได้ ใช้การยิงรับ | — |

ข้อสังเกต: Shopee `TO_RETURN` ใน os_orders = ลูกค้าขอคืนหลังได้ของ (ไม่ใช่ตีกลับ) แท็บ returning เดิมนับปนอยู่

## แนวทางที่พิจารณา

- **A (เลือก)** ยิงรับ + ดึงสถานะจากแพลตฟอร์ม — ครบเหมือน BigSeller ต้องมีตารางใหม่ 1 ตาราง
- B ยิงรับอย่างเดียว — ไม่รู้ว่าใบไหนควรถึงแล้ว, ใบลูกค้าคืนหาไม่เจอ → แทน BigSeller ไม่ได้
- C ดึงสถานะอย่างเดียว ไม่ยิง — ไม่รู้ว่าของถึงมือจริง ตอบคำถาม "ครบไหม" ไม่ได้

## ออกแบบ

### ข้อมูล — ตารางใหม่ `os_returns` (SQL `069_returns.sql`)
หนึ่งแถว = หนึ่งกล่องที่จะกลับร้าน
- `platform, shop, order_id` · `kind` = `failed` (ตีกลับ) | `buyer` (ลูกค้าขอคืน)
- `return_id` (ว่างสำหรับตีกลับ) · `ret_key` = return_id หรือ order_id — unique(platform, shop, ret_key)
- `tracking_no` = เลขที่อยู่บนกล่องตอนกลับมา (ตีกลับ = เลขขาไป, ลูกค้าคืน = เลขขากลับ) · `carrier`
- `items` jsonb `[{sku, name, qty, image}]` (ลูกค้าคืนอาจคืนไม่ครบทุกชิ้นในออเดอร์)
- `reason` · `state` = สถานะการคืน ใช้ชื่อเดียวกับ BigSeller (พนักงานคุ้น):
  - `waiting` รอคืนสินค้า — ตกลงคืนแล้ว รอลูกค้าส่ง
  - `transit` อยู่ระหว่างคืนสินค้า
  - `arrived` คืนสินค้าแล้ว — แพลตฟอร์มบอกถึงร้าน **หรือพนักงานยิงรับแล้ว** (TikTok ลูกค้าคืนไม่มีสัญญาณถึงร้าน BigSeller ก็ตั้งตอนยิง)
  - `failed` การคืนสินค้าล้มเหลว
  - `lost` สูญหาย
  - `not_needed` ไม่ต้องส่งคืน — คำขอถูกปิด/ปฏิเสธ/เปลี่ยนเป็นคืนเงินอย่างเดียว ระหว่างทาง (ซ่อนจากหน้า ยกเว้นยิงรับไปแล้ว)
  - ไม่เก็บ: "ยังไม่รับสินค้า" (คืนเงินอย่างเดียว) และ "อื่นๆ" (ยังเจรจา/คืนเงินอย่างเดียว) — ไม่มีของต้องกลับ จะเข้าตารางเมื่อเจรจาจบและต้องส่งของคืน
- `recv` = สถานะรับของ (แทน Stock-In ของ BigSeller ซึ่งร้านกด "ไม่ Stock-In" ทุกใบอยู่แล้ว):
  `null` ยังไม่รับ · `full` รับครบ · `partial` รับไม่ครบ (ระบุ SKU ที่ขาด + หมายเหตุ ใน `receive_note`/`missing` jsonb)
- `platform_status` (ข้อความดิบไว้ดู) · `started_at` (เริ่มเดินทางกลับ/ยื่นคำขอ) · `arrived_at`
- `received_at, received_by, receive_note` (คนยิงรับ)
- `checked_at` (ถามสถานะล่าสุดเมื่อไหร่ — ไว้หมุนเวียนถาม)
- ขนาด: ~400 ใบ/เดือน ใบละไม่ถึง 1 KB → ไม่ถึง 5 MB ต่อปี

### ดึงข้อมูล — `/api/sync/returns` + ตั้งเวลาใน netlify.toml (ทุกชั่วโมง)
1. **ตีกลับ**: ใบ os_orders ที่ `status='cancelled'` และ `collected_at` ไม่ว่าง → สร้างแถว `kind=failed` (ยังไม่มี)
2. **ลูกค้าขอคืน**: TikTok returns/search + Shopee get_return_list ตาม update_time ตั้งแต่รอบก่อน → upsert แถว `kind=buyer` (ข้าม "คืนเงินเท่านั้น"/ไม่มีเลขพัสดุขากลับ…ยกเว้นมีของต้องกลับ)
3. **ถามสถานะ** ใบที่ยังไม่ `arrived/lost` และยังไม่ยิงรับ ทีละไม่เกิน N ใบต่อรอบ (เก่าสุดก่อน) ด้วย tracking API ด้านบน
3b. **ออเดอร์ที่ยังขึ้น "กำลังส่ง" เกิน 2 วัน** (ย้อน 90 วัน ~340 ใบ) ถาม tracking ทีละ ~30 ใบ/รอบ — TikTok/Shopee ไม่ยกเลิกออเดอร์จนกว่าของจะถึงร้าน
   ระหว่างทาง BigSeller นับเป็น "อยู่ระหว่างคืนสินค้า" แล้ว (เทียบ 25 พ.ย. เจอ 19 กล่องแบบนี้) · TikTok action_code 702xx = กำลังส่งคืน
4. ย้อนหลัง **90 วัน** เท่า BigSeller (ผู้ใช้อยากให้ตัวเลขตรงกัน 80 / 1,050)

### นำเข้าไฟล์ BigSeller — ครั้งเดียว ไม่ทำปุ่ม (ผู้ใช้สั่ง 25 พ.ย.: "ใส่ไปเลยว่า stock in แล้ว")
- Claude นำเข้าเองหลังผู้ใช้รัน SQL: สคริปต์ `scripts/import-bigseller-returns.py` อ่านไฟล์ → upsert ลง os_returns ผ่าน REST (service key ใน .env.local)
- ไฟล์ "ส่งออก" จากหน้า การคืนสินค้า Stock-In (ตัวอย่าง `Order-Return202611251041308.xlsx` 25 พ.ย.):
  1 แถว = 1 SKU · 1,092 แถว = **1,050 กล่อง** ตรงกับแถบ "ไม่ Stock-In (1050)" เป๊ะ · Stock-In 27 ส.ค.–24 พ.ย.
- คอลัมน์ที่ใช้: แพลตฟอร์ม · ร้านค้า BigSeller · หมายเลขคำสั่งซื้อ · ID คำสั่งซื้อหลังการขาย (ว่าง = ตีกลับ) ·
  หมายเลขแทร็คกิ้ง / หมายเลขแทร็คกิ้งคืนสินค้า · SKU ร้านค้า · จำนวน · สาเหตุการคืนสินค้า · เวลาถึงคลัง · เวลา Stock-In · สถานะ Stock-In
- ร้าน: TT Solidsports→tiktok/SOLID · MVP→tiktok/MVP · SP Solid→shopee/SOLID · SP Realsports→shopee/REAL · SP MVP→shopee/MVP · LZD Solid Sport→lazada/SOLID
- แถวที่ "ไม่ Stock-In"/"Stock-In ทั้งหมด" → `recv=full`, `received_at` = เวลา Stock-In, `received_by` = 'BigSeller' (ไม่เก็บชื่อผู้ซื้อ/อีเมลผู้ดำเนินการ)
- ไม่ทับใบที่ยิงรับในระบบเราแล้ว · อ่าน xlsx ด้วย `readZip` ของ lib/xlsxPatch.js แบบ lib/r02.js (ไม่เพิ่มไลบรารี)
- Shopee MVP ไม่มี API (ร้านนี้อัปเดตผ่าน Mass Update) → ใบใหม่ของ SP MVP ระบบไม่เห็นเอง มีแค่จากไฟล์ (90 วัน 3 ใบ)

### หน้า `/returns` (เมนูใหม่ "ของคืน" ในแถบด้านบน)
- ช่องยิงบาร์โค้ดด้านบน: ปืนยิงแบบเสียบคอม (พิมพ์+Enter) และปุ่มกล้องมือถือ (ใช้ตัวอ่านเดิมของ Scanner)
  - หาจาก `tracking_no` ก่อน แล้วค่อยเลขออเดอร์ / เลขพัสดุออเดอร์ (บางใบกล่องคืนแปะเลขเดิม)
  - เจอ → จดรับทันที โชว์กรอบเขียวใหญ่: ร้าน · ประเภท · สินค้า SKU × จำนวน + รูป ให้เปิดกล่องเช็คของ
  - ยิงซ้ำ → บอกว่า "รับไปแล้วเมื่อ… โดย…" · ไม่เจอ → กรอบแดง + จดเลขที่ไม่เจอไว้ให้ดู
  - ชื่อคนยิงจำไว้ในเครื่อง (แบบ PullForm)
  - BigSeller ("สแกนเพื่อ Stock-in"): ยิงสะสมเป็นรายการ (≤500) แล้วกดยืนยันทีเดียว · ต้องเปลี่ยนแป้นเป็น EN ก่อนยิง · วางเลขหลายใบเป็นชุดได้ · มีอัดวิดีโอ
  - ของเรา (แก้ตามผู้ใช้ลองจริง 25 พ.ย.): ยิง → กรอบ **"รอตรวจ"** โชว์สินค้าที่ควรอยู่ในกล่อง (ยังไม่บันทึก) → เปิดกล่องเช็ค → กด **"ครบ ตกลง"** หรือ "ของไม่ครบ"
    · ยิงกล่องเดิมซ้ำ = ตกลง (แบบ BigSeller) · มีปุ่ม "ครบทั้งหมด ตกลง" · รายการรอตรวจจำไว้ในเครื่อง รีเฟรชไม่หาย
    · **ออเดอร์เดียวกันรวมกรอบเดียว** · ยิงไม่เจอ = ข้อความสั้นข้างช่องยิงแล้วหายไป ไม่ค้างเป็นกรอบแดงในรายการ
    · (ลองจริงรอบ 2) ยิงเข้ามา **ติ๊กครบทุกชิ้นไว้ให้เลย** ชิ้นไหนไม่มีค่อยกดให้เป็นแดง · ช่องยิงไม่ล็อกระหว่างค้น + เคอร์เซอร์กลับช่องยิงหลังกดปุ่ม → ยิงต่อเนื่องได้
    · **มีเสียง** (Web Audio ไม่ใช้ไฟล์): ติ๊ด = เจอกล่อง/ติ๊กสินค้า · ติ๊ด-ติ๊ด = บันทึกแล้ว · ตื๊ด ๆ = ไม่เจอ / รับไปก่อนแล้ว / ผิดพลาด
  - **แป้นไทยก็ยิงได้**: ถ้าโค้ดที่เข้ามาเป็นตัวไทย แปลงกลับเป็นปุ่มอังกฤษตามแป้นเกษมณีก่อนค้นหา
  - วางเลขหลายบรรทัดในช่อง (เช่นก๊อปจากไฟล์) = รับทีละเลข
  - ไม่ทำอัดวิดีโอ
  - ยิงแล้วถือว่า **รับครบ** ทันที มีปุ่ม "ของไม่ครบ" ให้ติ๊ก SKU ที่ขาด + พิมพ์หมายเหตุ → **รับไม่ครบ**
- แท็บหลัก (สถานะรับ แบบแถบ Stock-In ของ BigSeller): **ยังไม่รับ** · รับครบ · **รับไม่ครบ** · ทั้งหมด
- ปุ่มกรองสถานะการคืนพร้อมตัวเลข (แบบ BigSeller): รอคืนสินค้า · อยู่ระหว่างคืนสินค้า · คืนสินค้าแล้ว · การคืนสินค้าล้มเหลว · สูญหาย
- กล่องเตือนบนสุด: **⚠️ คืนสินค้าแล้ว แต่ยังไม่รับ N ใบ** (ตัวตอบ "ได้ครบไหม") + อยู่ระหว่างคืนเกิน 7 วัน
- กรอง: ประเภท (ตีกลับ/ลูกค้าคืน) · ร้าน · ช่องค้นเลขออเดอร์/เลขพัสดุ
- ติ๊กเลือกหลายแถว (หรือเลือกทั้งหน้า) → **ส่งออก** เป็นไฟล์ CSV เปิดใน Excel ได้ (มี BOM ภาษาไทยไม่เพี้ยน)
  คอลัมน์: แพลตฟอร์ม · ร้าน · ประเภท · เลขออเดอร์ · ID คืนสินค้า · เลขพัสดุ · SKU · ชื่อสินค้า · จำนวน · สาเหตุ · สถานะการคืน · สถานะรับ · เวลาถึงร้าน · เวลารับ · คนรับ · หมายเหตุ
  ถ้าไม่ได้ติ๊กอะไร ส่งออกทุกแถวตามตัวกรองตอนนั้น
- ทุกแถวมีปุ่ม "รับ" (กรณีบาร์โค้ดกล่องอ่านไม่ออก) + ปุ่ม "ดึงสถานะใหม่" บนหน้า
- ปุ่มของ BigSeller ที่ไม่ทำ: ลบออก (ใช้สถานะซ่อนแทน) · พิมพ์ Label SKU · ย้ายเข้า Fulfillment Warehouse · เครื่องหมาย (ใช้หมายเหตุแทน)
- ยกเลิกการรับได้ (ยิงผิดใบ)
- แท็บ "📦 ส่งแล้วตีคืน" ในหน้าออเดอร์เดิมคงไว้ ใส่ลิงก์ไปหน้าใหม่
